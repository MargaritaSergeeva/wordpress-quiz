# Архитектура и сопровождение

## Решения

Квиз — собственный тип записи `wpq_quiz`; схема вопросов хранится в метаданных.
Редактор меняет тексты, варианты и порядок без правки кода. От 1 до 30 вопросов,
от 2 до 20 вариантов, один ответ на вопрос. У вопросов и вариантов стабильные ID.
Блок Gutenberg и shortcode используют один серверный renderer. Каждый экземпляр
имеет собственный контекст Interactivity API и уникальные имена полей, поэтому
несколько одинаковых или разных квизов не конфликтуют на странице.

Динамический блок выбран для немедленного отражения правок редактора.
Interactivity API даёт штатный для WordPress механизм состояния без отдельного SPA.
Плагин независим от демонстрационной темы; архив можно установить на другом сайте
с совместимой версией WordPress/PHP. CRM URL и токен задаются на сервере через
`WPQ_CRM_URL` и `WPQ_CRM_TOKEN` (константы или окружение), а не через браузер.

## Работа редактора

В меню «Квизы» создайте запись, задайте название, вопросы и варианты, опубликуйте.
Кнопки перемещения меняют последовательность, удаление и добавление доступны в редакторе.
На странице вставьте блок «Квиз» и выберите запись. Альтернатива — shortcode
`[wordpress_quiz id="123"]`. Используйте ID созданного квиза вместо 123.
После изменения опубликованного квиза проверьте форму заново. Уже открытая старая
версия при отправке получит сообщение об обновлении вопросов, а не смешанные ответы.

## Поток данных

Браузер отправляет ID квиза, ревизию схемы, пары ID вопросов/ответов, контакты,
согласие и UUID отправки в REST endpoint `/wp-json/wordpress-quiz/v1/leads`.
Сервер проверяет типы, размер, публикацию, актуальность схемы, все варианты и контакты.
Тексты вопросов и ответов берутся с сервера. Заявка сохраняется в отдельную таблицу
с неизменным снимком текстов и временем согласия, после чего отправляется в CRM.

Уникальный request ID защищает от дублей при повторе одной отправки; изменение тела
с тем же ID отклоняется. CRM также проверяет ключ идемпотентности. Подтверждение формы
означает сохранение заявки в WordPress; при недоступности CRM она остаётся со статусом
ошибки и может быть отправлена повторно в «Квизы → Заявки». Статус «Доставлена»
выставляется только после успешного HTTP-ответа с CRM ID. Блокировка записи не даёт
двум процессам одновременно отправить одну заявку; зависшую попытку можно повторить
через 5 минут. Таблица заявок и повторная отправка доступны только администратору.

## Ограничения и развитие

- Первая доставка синхронная, таймаут 8 секунд. Для нагрузки нужны фоновая очередь,
  автоматические повторы с задержкой и оповещения о накоплении ошибок.
- Текущий адаптер работает с тестовым приёмником. Реальная CRM потребует маппинга,
  проверки авторизации, контрактных тестов и учёта её механизма дедупликации.
- Honeypot и ограничение отправок через transient — базовая защита, не защита от DDoS.
  Счётчик не атомарный; за reverse proxy без отдельной настройки адреса общий для посетителей.
  Для промышленного использования нужен лимит на reverse proxy и корректное доверие к proxy IP.
- Нет ветвления, файлов, множественного выбора и аналитики событий. Для ветвления
  расширить схему переходами по стабильным ID, проверять циклы/достижимость и
  валидировать на сервере именно пройденный маршрут; не привязывать переходы к индексам.
- Автоудаление заявок и инструменты экспорта/удаления персональных данных пока не реализованы.
  Перед реальным сбором согласовать сроки хранения и добавить эти механизмы.
- Резервное копирование отключено по условию владельца. Volumes переживают перезапуск,
  но не заменяют резервную копию и не защищают от удаления сервера.
- Тестовые условия согласия предназначены только для вымышленных данных.

Секреты не включены в Git, базу и CRM нельзя открыть через опубликованный порт.
WordPress доступен через localhost-порт и внешний HTTPS proxy; в админке отключён
редактор файлов. Сохранение схемы и повторная доставка проверяют права и nonce.
Публичный nonce не рассматривается как защита анонимной формы от спама.
